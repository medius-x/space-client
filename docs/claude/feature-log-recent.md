# Свежие фичи — решения

## Обложка игры в углу голосовой панели (КЛИЕНТ-ONLY, 2026-11-19)
Юзер-запрос: «если я в комнате и запускаю игру — в правом верхнем углу панели появляется значок игры; текстовая область чуть уезжает влево». Источник — уже копившийся кэш GameStore: `appStore.ownActivity` — НОВОЕ реактивное зеркало `broadcastActivityLine` (пишется при каждом флипе линии); `VoiceBar` селектит из него `igdbGameId` + из gameStore карточку → `t_thumb`-обложка `position:absolute` в углу `.voice-bar` (height 38, поверх зазора между инфо-строкой и кнопками, НЕ поверх кнопок), ховер = тултип с именем игры. Сдвиг: `.voice-bar-info.with-game-icon { padding-right: 44px }` + transition 0.15s — текст (flex:1, ellipsis) поджимается плавно; значок появляется/исчезает вместе с линией. Ручные виды (без igdbGameId) обложки не дают. Карточку собственной линии обеспечивает `ensureRosterGameCards` ЯВНО (ростер-эхо по таймингу не гарантирован) через activeSession под capability `igdb-games`; обе варианта панели (комната и звонок) рендерят одинаково.

## Перенастройка стука входа/выхода (КЛИЕНТ-ONLY, 2026-11-19)
Живые репорты: в игре стук не слышно. Раунд 1 (чистый ретюн 200/270 + октава) юзер отверг — «слишком высокий»; раунд 2 — **наложение по его же просьбе**: старый низкий корпус **150/210 остаётся телом ноты** (держит привычную высоту), сверху яркий слой **200/270 (0.6)** и его **октавный звон (0.35)** для пробиваемости, мастер **0.8** (был 0.5). Расписание чистое (`KnockNote`: frequencyHz/brightHz/overtoneHz), синтез в `notifications.playKnock` (общая огибающая на все три слоя). Регистр базы по-прежнему под deafen-подсказкой (280, тестится); отличает от глиссандо ритм двойного тука.

## Кнопки голосовой панели на всю ширину (КЛИЕНТ-ONLY, 2026-11-19)
`.voice-bar-buttons` была `justify-content: flex-end` — квадратные 30×30 прижаты вправо, слева «дыра». Теперь `flex: 1 1 0` на каждой кнопке (высота 30px и глифы не тронуты): ряд делится поровну, левый отступ = правому (паддинг карточки), межкнопочный 8px прежний. Оба варианта панели (комната и звонок) рендерят один и тот же набор из 5 кнопок в одном контейнере → ширины совпадают между режимами; при равном числе видимых кнопок.

## Глифы Material Symbols: игровая строка, пикер видов, список игр (КЛИЕНТ-ONLY, 2026-11-19)
Юзер принес набор с fonts.google.com/icons (**Material Symbols (new)**, outlined; MDI-аналоги явно отвергнуты — «не нравятся»). Решение: **SVG-пути, не второй иконочный шрифт** — горстка глифов не оправдывает ~300КБ variable-woff2 рядом с MDI; пути взяты из github.com/google/material-design-icons (symbols/web/<name>/materialsymbolsoutlined, Apache 2.0), вшиты в `components/MaterialGlyph.tsx` (сетка 0 -960 960 960, `currentColor`, размер 1em — класс `icon` рядом даёт font-size-сайзинг как у шрифтовых). Точки: (1) IGDB-линия — `sports_esports` вместо эмодзи 🎮: `ActivityLine`-компонент (ростер + строка правила) + список «Определённые игры» в Settings (там эмодзи был захардкожен отдельно — пропущен первым проходом, пойман смоуком юзера), `formatActivityLine` для igdb отдаёт голое имя (глиф — артовый, не текст); в ростере глиф +25% (`.member-activity .material-glyph { font-size: 1.25em }` — юзер-репорт «маленький слишком»); (2) пикер вида в Settings — ряд глиф-кнопок `ACTIVITY_KIND_GLYPHS` (playing=sports_esports · listening=headphones · watching=desktop_windows · streaming=live_tv · competing=**trophy** (scoreboard отвергнут смоуком — «табло, а не соревнование»); **custom — текст-чип**, у него и префикса нет), tooltip = старая локализованная метка (нативный `<select>` не умеет SVG — потому кастомный ряд). CSS: системная палитра нативных контролов (Field/ButtonBorder/Highlight), `.activity-kinds` 24px — новый драйвер высоты `.activity-add` (был нативный select), специфичность кнопок через `.activity-add`-префикс (поздний `.activity-add button` иначе перебивает). **Кнопка шаринга: `screen_share` пробовали и ВЕРНУЛИ `mdi-monitor-share`** (юзер-вердикт «старый всё-таки лучше») — screen_share из карты удалён. Бэклог-пункт «глифы префиксов» закрыт частично: префиксы ручных строк в ростере ОСТАЛИСЬ словами (не просили).

## Фикс шаринга: размер картинки у наблюдателя больше не пульсирует (КЛИЕНТ-ONLY, 2026-11-19)
Живой репорт (логи 2026-11-18): у наблюдателя разрешение скакало 1920×804↔1280×536↔960×402 (+1024×429/1536×643 от степпера поверх) десятки раз за вечер. Причина-цепочка: раунд 11.11 поставил энкодеру шара `degradationPreference = "balanced"` (боялись «enc 11 fps») → ЛЮБОЙ ход адаптивной потолки битрейта разрешает энкодеру менять разрешение; поп-аут релеит фриз ≥0.5с как «6% потерь» даже при lost+0 → лесенка режет ×0.7 → hold 15с → тихо → climb → фриз-репорт → режет… самоподдерживающийся цикл 30–60с, каждый ход = ресайз (сам ресайз инвалидирует цепочку декодера → PLI → фриз → репорт — усиление). Фиксы: (1) `maintain-resolution` (канон скрина: под нехваткой канала роняется fps/качество, НЕ разрешение; CPU-перегруз — работа степпера, он для этого и создан в тот же день); (2) детектор степпера переделан с fps-ratio (статичный контент легитимно кодирует ≪ входного fps → ЛОЖНЫЕ «encoder behind» по 3 раза за вечер) на цену кадра `totalEncodeTime/frames` против бюджета кадра (1000/inputFps): overloaded ≥80% бюджета 2 окна, relieved ≤50% 4 окна, окно без кадров = borderline; (3) «out:» в [share-stats] теперь честный — `outbound-rtp.frameWidth/Height` (закодированное), НЕ track-статистика (захват: вся сессия печатала 1920×804, пряча ресайзы — вагон времени на диагноз). Грабля в pitfalls: stats «track»-секции = захват, «rtp»-секции = провод. Смоук 19.11 (статика→движение): разрешение у обеих сторон неподвижно всю сессию, степпер молчит (на этом же паттерне раньше стрелял 3×/10 мин). Остаточное поведение (осознанное): на ПОЛНОСТЬЮ статичном экране freeze-статистика декодера растёт (плейаут стоит — нечего декодировать) → пара 6%-репортов → лесенка кратко режет до пола и восстанавливается сама за ~минуту после возобновления движения; размер не трогает, наблюдателю не видно (картинка и так стоит).

## IGDB-фаза 3: серверные игровые сессии (ПАРНЫЙ ДЕПЛОЙ, V21, 2026-11-19)
Фундамент ачивок: `game_sessions` на сервере (username, game, started/ended) — часы = SUM. Питание — Spring-события `GameActivityChangedEvent` из PresenceActivityTracker (каждый derived-переход, включая dampening-проглоченные). **Ручные playing-активности сессируют так же** (юзер-решение: от детектнутой ручную отличает только отсутствие меты): имя получает виртуальную карточку в igdb_games под ОТРИЦАТЕЛЬНЫМ id (одна на имя, case-insensitive; без жанров → в жанровые ачивки не попадёт; id ≤ 0 в IGDB не ходит). НЕ-playing и снятие линии закрывают сессии; скрытая юзером игра не репортится и не сессирует ВООБЩЕ (требование юзера: время с выключенным детектом не учитывается — by construction). Зависшие закрывает минутный sweeper по `PresenceTracker.isOnline` (реальная живость; инвизибл не мешает). `GET /api/games/my` (без rate limit, своя БД): карточка+часы(открытая сессия до now)+lastPlayed, newest-first, cap 30. Клиент: список «Определённые игры» теперь С СЕРВЕРА (локальный knownGames-MRU удалён), строка показывает часы (`formatPlaytime`: целые часы / минуты). **Ленивый рефреш карточек**: cache-hit при cached_at старше 24ч отвечает из кэша мгновенно, фоновая нить дообновляет byId (single-daemon lane + queued-set; saveCard перештамповывает TTL). Тесты: GameSessionServiceTest (7), интеграционник (событие→сессии→/my; refresh по TTL с timeout-verify).

## IGDB-автодетект игр (ПАРНЫЙ ДЕПЛОЙ с oak-server, round 1+2, 2026-11-19)
«Играет в …» без ручной привязки exe, **только Steam** (живой смоук-репорт 2026-11-19: авто-лестница для ЛЮБОГО приложения превращала клиент в машину вопросов — Chrome/Telegram и пр. с look-alike в IGDB открывали модалку каждые 5с; Discord-модель: автоматически детектятся только известные игры). Сигнал «это игра» = Steam appid: runtime спрашивает main-досье, БЕЗ appid exe молча резолвится в none (не-Steam — ручные правила как раньше; сам steam.exe не под steamapps/common → не детектится). С appid — серверная лестница (решения/гейты — oak-server docs/claude/security-operations.md): game → автолиния; Steam-установка, которой IGDB не знает → candidates → ОДНА модалка GamePickModal за сессию (клик = пин в ОБЩИЙ кэш сервера, скип → dismissed до рестарта). Клиент: `steam-games.ts` (main) — Steam-досье по exe (полные пути НЕ покидают main: `space-processes:gameIdentity` → {appId из appmanifest_*.acf, folderName}; кэш карты installdir→appid на жизнь процесса); runtime: полл 5с берёт ≤1 НОВОГО exe за тик (бюджет сервера 30/мин), `gameResolutions` Map (resolved/none/dismissed), вердикт `pickAutoGameLine` — LIFO как у правил; **ручное правило всегда главнее** автолинии; ApiError лестницы → пауза 60с. Wire: `PresenceActivity += igdbGameId` (append-only 3-е поле; СЕССИЯ СТРИПИТ его без capability `igdb-games`), обложка — прямой CDN `images.igdb.com/.../t_thumb/{coverImageId}.jpg` (публичный, без ключей), карточки чужих линий догружаются `GET /api/games/{id}` (404-id молчит всю сессию). GameStore — кэш карточек+pendingPick; галка «Определять игры автоматически» (гейт по capability, дефолт вкл; kill-switch активностей гасит и её). Смоук-факты: fuzzy-поиск IGDB СТРОГ (опечатки → пусто, не кандидаты) — appid-маршрут главный; `/v4/executables` — мусор (отброшен).

## Голосовые комнаты с лимитом участников (ПАРНЫЙ ДЕПЛОЙ, V18, 2026-11-18)
Discord-паритет: `channels.user_limit` (null=без лимита, 1..99, только VOICE). Гейт на сервере ПЕРЕД Janus-работой; **талон входа = живой токен комнаты, НЕ трекер-членство** (клиент шлёт `/app/voice.join` ДО `GET /room` — фаст-пас по трекеру пустил бы всех: живой репорт в тот же день); occupancy = UNION(трекер ∪ токены) **минус запросивший** (анонс в полёте — не место, иначе гонка блокирует первого входящего); снижение лимита никого не выкидывает; полна → **409** (НЕ 403 — клиент различает потерю CONNECT; в catch joinVoice: тост «комната заполнена» + ПОЛНЫЙ выход leaveVoice — отказ окончательный, никакой failed-панели с ручным «выйти», репорт 2026-11-18). Байпас — пермишшен JOIN_FULL_ROOMS: **первый REPURPOSE зарезервированного бита** (бит 14, бывший EMBED_LINKS; V16 вычистил маски, сидер не сеет; канал-скопед как CONNECT → оверрайды дают точечно). Клиент: `Channel.userLimit?` (append-only), счётчик «N/L» в строке канала (дробь = ГЛИФ, юзер-решение; `--sp-red` при N≥L), селект в CreateChannelModal + в настройках канала (AFK-таб → «Голос»-таб: лимит сверху, staged-Save применяет обе половины по-отдельности), capability `voice-user-limit` гейтит оба редактора (счётчику флаг не нужен — его нет без поля). AFK-свип ходит мимо /room → его move не гейтится (системное действие). Подробности — oak-server docs/claude/security-operations.md.

## SSH-харденинг при провижене (КЛИЕНТ-ONLY, фича 2 из беклога, 2026-11-11)
Галочка в Advanced → stage `harden` после register: ed25519-пара генерится `ssh2.utils.generateKeyPair` (aes256-ctr + bcrypt, passphrase ≥8 — НЕ персистится), pubkey идемпотентно в authorized_keys, **key-login доказывается вторым соединением ДО любых правок sshd**, затем `/etc/ssh/sshd_config.d/99-space-hardening.conf` (PasswordAuthentication/KbdInteractive no; только при живом Include-пробе), `sshd -t` с откатом конфига при reject, reload. Любой провал до reload оставляет парольный SSH нетронутым. Пара сохраняется в KV `ssh-access:<host>` (sanitize в domain/provisioning/ssh-access.ts); повторный прогон с passphrase подставляет пару в params.sshKey (transport ходит буфером вместо файла). Restored-ветка не харденит (первая партия). Швы транспорта: generateKeyPair/verifyKeyLogin (фейки в FakeProvisioningTransport).

## DFN3: слайдер потолка подавления + самотест (КЛИЕНТ-ONLY)
Единственная ручка vendored wasm — `df_set_atten_lim` (потолок дБ на кадр; 0 = лимитер выкл = сильнейшее); старый слайдер 0..100 — весь диапазон вне слышимости. Самотест runNoiseEngineSelfTest: onset duck/recovery/steady + AGGRESSIVE; steady верифицирует потолок; замер от сэмпла 1 (сэмпл 0 = латентность движка). Замер: потолок 15 → recovery ~125мс, steady −14.9 дБ — работает; «секундные» просадки были безлимитом; RNNoise без потолка → onset неизмеримы.

## Жёлтый AFK-статус в ростере (ДЕПЛОЙ ПАРНЫЙ — сервер первым; ПЕРЕДЕЛАН 2026-11-04)
**Переделка:** точка = «человек не у компа», а НЕ «молчит в голосе» — решение на КЛИЕНТЕ, не зависит ни от голосовой комнаты, ни от серверного таймаута AFK-канала (разные сущности). `afk-activity.ts`: `ROSTER_AFK_AFTER_SECONDS=300` (юзер: 5 мин) + `isRosterAway(idle, speaking, streaming)` = нет системного ввода + не говорю + не шарю; голосовой heartbeat (`isAfkActive`, грейс 60 с) не тронут — кормит свип AFK-комнаты. Runtime: тикер (main-owned `space-afk`) армится ОДИН раз в `bootstrapApp` на всю жизнь приложения (был привязан к joinVoice/teardownVoice); тик ведёт ДВЕ ветки — голосовой heartbeat при живом голосе + флип `currentRosterAway` всегда; флип → `broadcastRosterAfk` по ВСЕМ живым сессиям (активная + фоновые: ростер каждого сервера показывает юзера). `ConnectionSession.reportRosterAfk(afk)` хранит `rosterAfkSent` как желаемое состояние и (пере)доставляет его в `start()`/`resyncAfterReconnect()` — флип в окне реконнекта не теряется (stomp.send при разрыве = тихий скип). Логи: голосовой verdict-трейс только в голосе, roster — только флипы (`roster afk: away|back`). Сервер (см. oak-server): `/app/roster.afk` + `RosterAfkTracker`; wire `/topic/voice.afk`/`GET /api/voice/afk`/`VoiceAfkStatusEvent` сохранены — 0.5.x-клиенты рендерят новые события без правок. Отображение не менялось: RosterStore `afk`-множество (snapshot/delta-дисциплина presence; offline-дельта гасит жёлтый), гейт **capability `afk-roster`**, `rest.getVoiceAfk` 404-толерантен, Avatar `away` → `--sp-yellow`.
**Правка 2026-11-19 (живой репорт: слушающий шаринг с тихим миком желтел):** `isRosterAway(idle, inVoice)` — живая голосовая комната или 1:1-звонок (`inVoiceOrCall()`) = присутствие ПО ОПРЕДЕЛЕНИЮ, авто-жёлтая невозможна (Discord-паритет; мгновенный срез speaking у 30-с тика не годится — слушающий не попадает в срез). ## Миграция server-to-server (ДЕПЛОЙ ПАРНЫЙ — сервер первым)
Вариант B: новый сервер сам тянет бэкап со старого (curl + одноразовый токен), компьютер = control plane; fallback «через компьютер» навсегда (легаси/за NAT/провал пробы). Решения: TTL токена 2 часа (30 минут истекали бы посреди restore); PEM серта захватывает клиент одноразовым `session.setCertificateVerifyProc` (сервер Caddy-серт не читает; сверка с TOFU-пином записи); Range/206 на /file обязателен (иначе `curl -C -` = ошибка 33). Сервер: POST/DELETE `/api/server/backup/migration-transfer` (Bearer, requireAdministrator, 409 без архива; ответ {token, expiresAt, archiveSha256, archiveBytes}); GET `/api/server/backup/transfer/{status,file}` — permitAll, весь гейт в заголовке `X-Space-Migration-Token`; токен single-slot, многоразовый до ревока («одноразовость» = deliver-and-delete архива). **ServerCapabilities.FEATURES += `server-migration`**. Клиент: `migrationTransfer` (params.ts: sourceUrl https-only, token base64url, sha hex-64, certificatePem; взаимоисключение с backupArchivePath); restore: `.migration-auth` 0600 (Ssh2Transport.writeFile += mode) + old-ca.pem → downloadOnServer → `sha256sum -c` → scrub; backup-schedule.ts: suppress расписания старого сервера на окно миграции (подменит single-slot архив), отпуск в succeeded/failed/cancel; флоу: съёмка → (capability) issue → probe → direct / fallback download + hashFile; finally: ревок (только fallback). IPC `provisioning:probe-migration` (main резолвит persistedPinForHostname) и `provisioning:hash-file` (гейт temp/downloads); cancelProvisioningRun: сперва `pkill -f space-provisioning-download` (закачки отвязаны от SSH; UA-маркер в argv). Security: 404 на пустой слот неотличим от «нет токена»; токен в 0600-файле, не в cmdline.

## Бэкап сервера + restore при провижининге + Migrate

Деплой парный: сервер первым, клиент следом. Блок клиента гейтится capability `"backups"` (ServerProfile.capabilities; первое использование `hasServerCapability()`): профиль присваивается в start() до permissions-снапшота; поздние /topic/server-пуши его не меняют; старый сервер → блок скрыт целиком, вкл. Migrate.

Серверная половина (детали — oak-server/CLAUDE.md): REST `/api/server/backup` run (202, claim синхронно — всегда running=true) / status / estimate / file (стрим); гейт всех — `requireAdministrator` (MANAGE_SERVER НЕ проходит — юзер); дамп TRUNCATE'ит всё КРОМЕ flyway_schema_history и refresh_tokens — миграция = честный ре-логин (.env убивает JWT); RestoreRunner: env `oak.restore.file`+public-*; manifest-гейт Flyway; маркеры `RESTORE COMPLETED`/`FAILED` грепает провижининг.

Клиент: Server Settings → Backups (гейт owner||ADMIN-бит). «Download latest» рендерится только при `status.fileAvailable===true` (нет у старого сервера → не гасится): перекачать неотданный буфер; после полной доставки сервер копию УДАЛЯЕТ; «Delete archive» → REST `discardBackupArchive()` (DELETE /file, 204). SPACE-гейт: estimate += `availableBytes` (-1 = нечитаемо); нехватка → подтверждение DISABLED (ENOSPC); -1 → без блокировки.

Расписание КЛИЕНТСКОЕ (`renderer/backup-schedule.ts`): per-record `ClientSettings.backupSchedules {enabled, minuteOfDay}`; срабатывает только при живом клиенте, догона НЕТ (юзер); папка/retention глобальные — `backupFolder`/`backupKeepCount`. RETENTION ТОЛЬКО автоматический (юзер): prune только после планового скачивания; ручные кнопки не удаляют.

Мост `spaceBackup` (electron/backups.ts): MAIN стримит URL в файл (не ArrayBuffer в рендерере); имена basename; папка из KV main, не из запроса; target "temp" — one-shot в tmp/space-migrate. prune: префикс `server-backup-<host>-` под `^[\w.-]+$`.

Провижининг-restore: `ProvisioningParams += backupArchivePath` (main проверяет существование до прогона). Restore-режим: env += `OAK_RESTORE_FILE=/restore/backup.zip` + `OAK_RESTORE_PUBLIC_HOST/PORT/SCHEME`; START_ORDER БЕЗ oak; полл docker-логов на маркеры (провал = ProvisioningFailure с причиной); needsLoginRestored: register НЕ выполняется (вход паролем исходного владельца). Restore на ADOPT (живой compose) = отказ. Compose-шаблоны в env/ и electron/provisioning/files/ — синхронно.

Migrate: съёмка бэкапа = ПЕРВЫЙ шаг прогона (юзер: скачивание после старта миграции; при ошибке/отмене архив удаляется). `ProvisioningPanel mode="migrate"`: стадия "backup" первой в STAGE_ORDER (синтезируется локально) → `takeMigrationBackup(session, shouldAbort)` → `provisioning.start(backupArchivePath + migrationArchive:true)`. temp чистит IPC `space-backup:deleteTemp`; FINALLY прогона удаляет архив (гейт path.relative). Архив строго one-shot.

Принятые границы: restore-архив = доверенный ввод уровня jar-override (подмена = произвольный SQL на новой машине); backupArchivePath — тот же renderer→main file-read класс, что jarPath/sshKeyPath.
