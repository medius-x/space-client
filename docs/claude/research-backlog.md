## Session-end сигналы (shutdown при окне в трее)

- Close-to-tray-гвард не отличает shutdown Windows от X: OS жёстко терминирует процесс → teardown голоса нет, фантом-тайлы у пиров до таймаута Janus (~1 мин).
- Ловить session-end (`app.on("session-end")` / WM_QUERYENDSESSION; проверить доставку в 44.x) → initiateGracefulQuit или fire-and-forget janus destroy; оценить logoff vs shutdown.

## Голос: ревизия оптимизаций (клиент-only) — ОТЛОЖЕНО до полевых данных

- Ревизия 2026-11-17 (sfu.ts / janus.ts / RoomAudio.ts / rejoin+uplink-лестницы runtime / peer-call.ts) при НУЛЕ открытых репортов: стек вылизан, каждый watchdog — шрам живого инцидента; главный риск — не недооптимизированность, а регрессия от бессимптомной переделки выстраданных контрактов. Решение: ничего не менять до полевых данных; телеметрии (RTT-бейдж, inbound-line, share-counters, stall-autopsy) для диагностики по логам достаточно.
- Кандидат 1 (взять в полевой смоук): `maxev=1` в janus long-poll — ОДНО событие на запрос; в населённой комнате burst флипов (мьюты/входы/шары) выгребается последовательными round-trip'ами, добавляя задержку каждому следующему. `maxev≈10` — штатный параметр HTTP-транспорта Janus (срезает и задержку, и число запросов); это wire-поведение → поднимать только с живым смоуком, в 0.5.3 с другом глянуть очереди событий в логах.
- Кандидат 2 (микро, потом): ICE-restart лестница p2p-звонков бесконечна (1→2→4→8→16 с forever) — при намертво мёртвом пире звонок «реконнектится» вечно вместо честного фейла с кнопкой перезвонить. Cosmetic-класс, чисто клиентское, capability не нужен.
- ОТКЛОНЕНО: остановка `<audio>`-носителя voice-цепей при живом граф-плейауте (экономия декодера на участника) — element-паттерн исторически защищает от Chromium-граблей доставки фреймов; трогать носитель без симптома = способ получить «пропавший голос». Jitter-buffer/опус-тюнинг голоса — то же: стек Chromium справляется, стерео голосу не нужно by design.

## Войс-морфер: пара пресетов (клиент-only)

- Топология = нойзодав (media/noise-suppression.ts): mic → эффекты → processed-трек; оба пути (SFU + 1:1) его умеют — морфер сиблинг NS-движка, сервер/Janus/wire не трогаются; ВЫКЛ = шунт (родной трек).
- Radio = BiquadFilter bandpass 300–3400 Гц + WaveShaper + DynamicsCompressor; Robot = ring modulation; Pitch = `@soundtouchjs/audio-worklet` (AudioWorklet вне main-нити) — ресинтез руками НЕ писать.
- Дроп-ин войсчейнджера под WebRTC-микрофон в JS нет; Tone.js и GStreamer отвергнуты.
- Серверный мьют (Janus moderate) не задет — режет m-line, не сигнал; смена эффекта вживую = replaceTrack; кривые — на слух.
- UI: селектор off/radio/robot/pitch (voice-панель + Settings → Audio), настройка локальная.

## E2E шифрование личных сообщений 1:1 (wire, сервер M / клиент L)

- Полный E2EE отклонён ранее (ломает поиск/mention-механику всего чата). DM-only
  снимает главные возражения: собеседников два, групповых сущностей нет, а
  единственный настоящий поиск по DM (channel-скоуп «This DM») имеет нулевую
  обнаружимость — поле скрыто в Home (правой колонки нет, открывается только
  Ctrl+F, кнопки-лупы в UI не существует) и им не пользуются.
- Ключевая модель: identity-пара X25519 на юзера (приватная — локальный KV,
  публичная — новый мини-эндпоинт), ключ пары DM = ECDH, сообщения AES-GCM,
  content = маркер+ciphertext (либо отдельное append-only поле — парный
  релиз). Криптография — WebCrypto (X25519/AES-GCM в Chromium), НОЛЬ новых
  зависимостей. Легаси-сообщения остаются плейнтекстом, маркер различает —
  capability не нужен.
- Мультидевайс — ВАРИАНТ А (user decision 2026-11-18): один identity на юзера,
  приватный ключ синхронизируется между своими устройствами вручную (QR/фраза
  при подключении нового девайса) — «E2E-lite» против пассивного оператора
  VPS, модель тривиальна. Вариант Б (prekeys per-device, честная PFS через
  полноценный протокол с сессиями) отвергнут: объём ×2-3 при угрозе, которую
  вариант А полностью закрывает; слабое место А — момент передачи ключа —
  принять осознанно.
- Потери при E2E (уточнено 2026-11-18): серверный поиск по DM (channel-скоуп;
  «everywhere» DM и так не знает) + поиск по именам файлов; mentionCount явных
  @ников в 1:1 (бесполезен — уведомления в DM не гейтятся по упоминаниям);
  серверный `ReplyInfo.preview` → preview шифровать клиентом при создании
  реплая; форварды DM→канал — только клиентский расшифр+перешифр (паттерн
  cross-instance ре-аплоада аттачей).
- Выживает: reply-пинг (живёт на `replyToId` — метаданные, не контент);
  подсветка @ника (клиентский матчинг в расшифрованном тексте, рендер и так
  клиентский); unread-бейджи/lastRead (id-based); вложения (клиент шифрует
  байты до presigned PUT; dims/видео-превью и так клиентские).
- Каскад точек расшифровки (аккуратная клиентская работа): MessageRow,
  превью последнего сообщения в DM-сайдбаре, QuoteCard, тосты.
- Групповые DM — ВНЕ scope (плейнтекст со всей механикой пингов).
- UX: замочек в DM-хедере; opt-in per-DM vs все DM сразу — мелкая развилка.
- Микро-задача «кнопка-лупа поиска в DM-хедер» РЕАЛИЗОВАНА отдельно от E2E
  (2026-11-18, вместе с выравниванием полосы хедера DM под линию поисковой панели).

## Ачивки: сбор телеметрии (фаза 1) + движок (фаза 2) — проработка 2026-11-24, НЕ реализовано

Исходник — юзер-список из 31 триггера (2 про опросы исключены: фичи нет; «Космос» = SPACE).
31 триггер сводится к 9 типам: часы в игре/множестве игр, часы по категории, голос-часы
(mic on/off/any, подряд|суммарно), together-часы (N в одной игре+канале, я участник|посторонний),
шаринг-часы, просмотр-часы, login-стрик, совпадение процессов (SPACE+Discord), ручные.

**Решения юзера (фиксировать, не переспрашивать):**
- Захардкоженный набор ачивок; JSON-конструктор условий ОТВЕРГНУТ.
- Сейчас реализуется ТОЛЬКО сбор событий (фаза 1); движок/UI — фаза 2.
- Телеметрия — пассивно сбоку от основной логики (по сигналингу, как отображение):
  хук в одну строку в существующих точках, ошибки записи НЕ роняют основной путь.
- Self-mute only: принудительный/implied mute НЕ считается «выключенным микрофоном»;
  «с включённым» = голос-время минус self-mute-интервалы.
- «12 ч подряд» — в ОДНОМ канале (выход/переход/разрыв рвёт серию — но см. сглаживание).
- Франшизы ЦЕЛИКОМ: Battlefield/GTA/TES/WoW-семейство; Dota 2+LoL = одно множество.
- Discord-совпадение — фильтрация списка процессов в СУЩЕСТВУЮЩЕМ 5-с тике
  (проверку discord.exe ставить ДО early-return тика); на сервер — только булев факт эпизода.
- Сглаживание разрывов — ДОБАВЛЕНО юзером: склейка серий ПРИ ЧТЕНИИ (не при записи!).
- Обязателен механизм логгирования ошибок/здоровья сборщика.

**Аудит-факты (что уже есть / чего нет):**
- ПОКРЫТО: `game_sessions` (V21, username × igdb_game_id × started/ended, sweeper) +
  `igdb_games.genres` (JSON) → бесплатно закрывают 12/31: все «часы в игре X» + жанровые
  (гонки/стратегии/шутеры/stealth — проверить, genre ли Stealth в IGDB или theme).
- НЕ собирается: голос-интервалы (VoiceMembershipTracker — чистый in-memory), mute-флипы
  (in-memory наборы трекера), шаринг экрана/камеры (мимо сервера — публикация прямо в Janus;
  voice.activity = пустой body, registry хранит только timestamp), просмотр чужих стримов
  (подписки в Janus, серверного маршрута нет), дни присутствия (только users.last_seen_at —
  одно значение; refresh_tokens чистятся через 30 д), история модерации (users.banned —
  boolean без журнала; timed-банов нет ⇒ ЛЮБОЙ unban = ручной by design).

**Фаза 1 — сбор (реализуемое):**
- Сервер V29 (V28 занял polls 2026-11-25), 7 таблиц: `voice_sessions` (username, channel_id, joined_at, left_at NULL=открыта),
  `voice_mute_intervals` (self-mute, закрывается на unmute/leave), `share_intervals`,

- 3 STOMP-приёмника: `/app/voice.share {channelId, sharing}`, `/app/voice.watch

- Клиент: репорт share start/stop (shareTarget/toggleCamera + редоставка на реконнекте —

  Ошибки отправки не трогают голос/шаринг.
- TelemetryRecorder (единый писатель): каждый вызов try-catch — WARN с контекстом
  (kind, username, channelId, исключение), основной путь живёт; пишущие методы
  @Transactional (урок TransactionRequiredException-саги: тесты хуков — настоящая БД
  БЕЗ @Transactional-подарков сверху); часовая INFO-сводка в стиле [JPA-OK]:
  `telemetry: recorded N (voice X, mute Y, share Z, watch W, presence D, moderation M),
  dropped K` — видно и аварии, и «тихо, потому что ничего не пишется»; выгрузка —
  существующий GET /api/server/logs.
- Категории: жанры IGDB из кэша; кураторские константы в коде для не-жанровых —
  Soulslike, WH40k, PS-порты, франшизы: name-паттерны (ILIKE 'Battlefield%') по ФАКТИЧЕСКИ
  ИГРАВШИМ играм кэша + ручные дополнения igdb_id. platforms у IGDB НЕ тянем (отвергнуто —
  вес ради одной ачивки). Manual-игры (отрицательные id, genres=[]) в жанровые не попадают.
- Сглаживание: серии «подряд» склеиваются ПРИ ЧТЕНИИ оконной функцией — интервалы того же
  юзера+канала с разрывом < 2 мин = одна серия; суммарные часы = СУММА фактических
  интервалов ⇒ gap-время никогда не начисляется, накрутка join/leave-циклами невозможна;
  грейс нужен только «12 ч подряд» (цена — минуты шума на серию); share/watch/mute —

## A. Очистка диска аттачментами, не снос сообщений (M, 3 фазы)

- StorageGcService.runOnce = sweepOrphans → (used% > high) → purgeBelowLowWatermark (старейшие сообщения; пины/min-keep иммунны) → VACUUM FULL; аттач-сущности в БД нет (JSON messages.attachments), объекты в MinIO; форварды шарят ключи (attachmentExists в purgeBatch защищает).
- Шаг detachAttachments МЕЖДУ orphan-свипом и purge: помечать аттачи старейших сообщений `purgedAt` (AttachmentRef += append-only, без миграций БД), объекты — через посмертную проверку; до low watermark; иммунные исчерпаны → прежний purge сообщений.
- Иммунитет: count (аттачи последних N сообщений) | age (всё свежее X часов); «последние N аттачментов» = N последних сообщений с аттачами по id desc (механика minKeepMessages).
- Политика: колонки ServerProfile у watermark'ов + расширение PUT /api/server/storage + строка в Server Settings → Server; StorageGcReport += detachedAttachments/detachedBytes.
- Клиент обязателен (иначе «вечный loading»): AttachmentRef += purgedAt + tombstone-рендер (прецедент `.message-sticker-dead`) — плейт «removed by storage cleanup», estimateRowHeight не растёт; помечать, НЕ удалять реф (attachmentExists перестаёт матчить).
- Грабли: sweep-grace-days (mtime-орфаны) ≠ age-иммунитет — не смешивать; usage() меряет overlay /app — MinIO-volume на том же диске; GC не листит custom-emojis/stickers/avatars.

## B. Bot API (M, 4–5 фаз)

- Фундамент oak-server совместим: POST /api/channels/{id}/messages под Bearer; STOMP /ws (Authorization в CONNECT); idempotencyKey; CORS не мешает.
- Дыры: bot-флага на User; долгоживущих непользовательских токенов (refresh одноразовый + family-reuse-detection); админ-создания аккаунтов (invite-only); per-bot rate limit; доки; UI.
- Миграция `users += bot boolean` + `bot_owner_id`; таблица bot_tokens (SHA-256, калька RefreshToken); токен показывается ОДИН раз, без expiry, ревок админом; тот же Bearer — фильтр после провалки JWT ищет хеш (in-memory кэш).
- `POST /api/bots {username, nickname}` (гейт MANAGE_MEMBERS или только OWNER — развилка) → 201 {user, token}; `DELETE /api/bots/{id}`; перевыпуск отдельным PUT. Права ШТАТНЫМИ ролями (assignRoles есть).
- Rate limit пер-бот на POST messages (LoginRateLimiter-калька, ~30/10 мин) → 429; события — STOMP as-is, бот подписывается per-channel, реконнект его забота.
- Клиент: UserSummary += bot (append-only, ПАРНЫЙ деплой) + бейдж BOT; UI создания потом (MVP = curl). Дока: oak-server docs/BOT-API.md + echo-бот на node + ссылка из README.
- Грабли: banned/removed гейты на CONNECT уже работают; бот-токен не JWT — переименование бота его не гасит; идемпотентность-кеш пер-юзер — ботам слать с ключом.
